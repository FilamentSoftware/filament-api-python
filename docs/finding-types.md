# Finding Entity & Connection Types

Almost everything you send to or receive from the backend is a typed dataclass.
This page explains **where those types live**, **how they are named**, and **how
to discover the fields on any given type**.

## The shape of `filament.types`

All public types are re-exported from `filament.types`, so in day-to-day code you
import from there regardless of which file a type is defined in:

```python
from filament.types import UserEntity, UserStatusEnum, ReadDataRequest
```

Under the hood, `filament.types` aggregates three groups:

```text
filament/types/
├── conditions.py     # DbConditionInstance hierarchy (see Conditions guide)
├── options.py        # DataOption (see Data Options guide)
└── generated/        # auto-generated from the backend — the bulk of the types
    ├── api.py          # ClientMethods / ServerEvents protocols (the wire contract)
    ├── base/base.py    # EntityBase, Entity, EntityConnection… (the root classes)
    ├── entities/       # every entity type, grouped by backend service
    ├── connections/    # every connection (relationship) type, grouped by service
    ├── enums.py        # every enum
    └── misc.py         # request/response/envelope types (ReadDataRequest, …)
```

## Generated code is read-only

Everything under `src/filament/types/generated/` is produced by the backend's
**Filament GenerateCode** tool. Each file starts with `# Generated by Filament
GenerateCode`.

> **Do not hand-edit generated files.** Any change is overwritten on the next
> codegen run. If you find a bug or a missing field, describe the fix in terms of
> the code-generation logic and raise it upstream rather than patching the output.

## Entity types

Entity types model the nouns of the platform (users, tasks, scopes, events…).
They live in `filament/types/generated/entities/`, **one file per backend
service**. Every entity ultimately derives from
[`EntityBase`](#the-base-class-hierarchy).

Import them from `filament.types`:

```python
from filament.types import UserEntity, TaskEntity, ScopeEntity
```

### Where each entity lives

The file name is the backend service: `user_service.py` holds `UserEntity`,
`UserAddressEntity`, … ; `task_service.py` holds `TaskEntity` and friends; and so
on. Each file's `__all__` lists exactly what it exports.

For the **complete, always-current list** of every entity — with its fields,
types, and a one-line description — see the auto-generated
[Type Reference → Services](type-reference.md#services) (entities and
connections are grouped by service there). That catalogue is
regenerated from the source on every codegen run, so it never drifts; this page
deliberately describes the *structure* rather than duplicating the list.

> The `…Base` classes (e.g. `UserBaseEntity`, `AddressEntityBase` in `generic.py`)
> are shared parents, not types you read or write directly — the catalogue tags
> them *(abstract base)*. The concrete types (`UserEntity`, `UserAddressEntity`, …)
> extend them.

To enumerate the entities available in a given install at runtime:

```python
import importlib
import pkgutil
import filament.types.generated.entities as entities_pkg

for module in pkgutil.iter_modules(entities_pkg.__path__):
    mod = importlib.import_module(f"{entities_pkg.__name__}.{module.name}")
    print(module.name, getattr(mod, "__all__", []))
```

## Connection types

Connection types model the **relationships** between entities — a connection has
a `from_id` and a `to_id` linking two entities. They live in
`filament/types/generated/connections/`, again one file per service, and derive
from [`EntityConnection`](#the-base-class-hierarchy).

```python
from filament.types import UserSkillConnection, TaskDependencyConnection
```

### Where each connection lives

As with entities, the file name is the backend service, and each file's `__all__`
lists what it exports (e.g. `user_service.py` → `UserSkillConnection`,
`UserPermissionsRoleConnection`).

For the **complete, always-current list** — with each connection's fields and
description — see the auto-generated
[Type Reference → Services](type-reference.md#services), where each service lists
its entities and then its connections.

> Names ending in `_1` / `_2` (e.g. `GenericUserSkillConnection_1`) are generic
> base connections; the suffix is the arity of their type parameters, and the
> catalogue tags them *(generic base)*. The concrete connections you use
> (`UserSkillConnection`, …) specialise them.

The runtime-enumeration snippet above works for connections too — just swap
`entities` for `connections` in the import.

## Enums

All enums live in a single file, `filament/types/generated/enums.py`, and are
re-exported from `filament.types`:

```python
from filament.types import UserStatusEnum, TaskStatusEnum, DataRequestAction
```

For the **complete, always-current list** of every enum and its members, see the
auto-generated [Type Reference → Enums](type-reference.md#enums). The two
conventions below are worth knowing regardless of which enum you reach for.

### `None_`: the renamed `None` member

Python reserves `None`, so any backend enum member literally named `None` is
generated as **`None_`**. For example:

```python
from filament.types import SubscriptionMode, ErrorCodes

SubscriptionMode.None_   # the "no updates" mode
ErrorCodes.None_         # "no error"
```

The serialization layer maps `None_` back to `None` on the wire automatically.

### `Flag` enums combine with bitwise operators

A few enums are `Flag` enums (`DataProcessingStatus`, `SubscriptionMode`,
`AvailabilityRepeatDaysEnum`, `PermissionAction`). Combine their members with
`|`:

```python
from filament.types import DataProcessingStatus, SubscriptionMode

status = DataProcessingStatus.Pending | DataProcessingStatus.Complete
mode = SubscriptionMode.Data | SubscriptionMode.Progress
```

`DataProcessingStatus.All` is a pre-combined shortcut for
`Pending | Processing | Complete`.

## Request, response, and envelope types

The types you build to make requests, and the payloads you get back, live in
`filament/types/generated/misc.py`. The ones you will use most often:

| Type | Used for |
| ---- | -------- |
| `ReadDataRequest`, `ReadDataTypeRequest` | Reading entities ([guide](reading-data.md)). |
| `ReadConnectedDataRequest`, `ReadConnectedDataTypeRequest` | Reading entities via a connection. |
| `ModifyDataRequest` | Creating/updating/deleting ([guide](modifying-data.md)). |
| `SubscriptionConfig` | Configuring a subscription ([guide](subscriptions.md)). |
| `ServiceDataRead` | The payload returned by `read_data`. |
| `ServiceDataUpdate` | The payload delivered to subscription callbacks. |
| `WrappedEntity` | An entity plus its permissions/pending-operation metadata. |
| `ValueOrErrorPublic_1[T]`, `SuccessOrErrorPublic` | The success/error envelopes every call returns ([reference](api-reference.md#the-response-envelope)). |
| `SubscriptionId`, `RequestId` | Identifier wrappers returned by `subscribe` / `modify_data`. |
| `ProcessingStatus` | Delivered to processing-lifecycle callbacks. |

## The base-class hierarchy

Defined in `filament/types/generated/base/base.py`:

```text
SpecifiedPropertiesBase          # tracks which fields you set (partial updates)
└── EntityBase                   # id, created_at/by, updated_at/by, scope_id
    ├── Entity                   # base for ordinary entities
    │   └── (every concrete *Entity)
    └── EntityConnectionBase     # adds from_id, to_id, from_entity, to_entity
        └── EntityConnection
            └── EntityConnection_2[TFrom, TTo]   # generic typed connection
```

Every entity therefore carries these common fields from `EntityBase`:

| Field | Type | Notes |
| ----- | ---- | ----- |
| `id` | `UUID` | Auto-generated (UUIDv7) on construction if you don't supply one. |
| `created_at` | `datetime` | |
| `created_by_id` | `Optional[UUID]` | |
| `updated_at` | `datetime` | |
| `updated_by_id` | `Optional[UUID]` | |
| `scope_id` | `Optional[UUID]` | |

Connections additionally carry `from_id`, `to_id`, `from_entity`, and `to_entity`.

The `SpecifiedPropertiesBase` parent is what makes **partial updates** work: it
records exactly which keyword arguments you passed to the constructor, so the
serializer only sends those fields. See
[Modifying Data](modifying-data.md#partial-updates-and-specified_properties).

## Discovering the fields on a type

Because every entity is a `@dataclass(kw_only=True)`, you have several easy ways
to see its fields without leaving your editor or REPL.

**Read the source.** The generated class carries the backend's documentation as a
docstring with one `:param:` line per field, e.g. in
`entities/user_service.py`:

```python
@dataclass(kw_only=True)
class UserEntity(UserBaseEntity):
    """A user entity that gives basic details about a user of the system.

    :param schedule_status: Represents whether the user should be included in schedules or not.
    :param given_name: The given name for this user.
    ...
    """
    schedule_status: UserStatusEnum = field(default=UserStatusEnum.Disabled)
    given_name: str = field(default='')
    ...
```

**Inspect at runtime** with `dataclasses.fields`:

```python
from dataclasses import fields
from filament.types import UserEntity

for f in fields(UserEntity):
    print(f.name, f.type)
```

**Let your IDE/mypy help.** Because the fields are real dataclass attributes with
type annotations, autocompletion and `mypy --strict` both understand them. The
[mypy plugin](conditions.md#static-validation-with-the-mypy-plugin) goes further
and validates field names *inside* the condition builder.

## Naming: snake_case vs camelCase

The backend wire format is camelCase; the Python types are snake_case. The client
converts between them automatically for entity (de)serialization and for the
typed `Condition` builder.

| Where | Which casing |
| ----- | ------------ |
| Python attribute access (`user.given_name`) | snake_case |
| `Condition(UserEntity).prop("given_name")` | snake_case (validated, converted for you) |
| `properties=[...]` projection list in a read request | **camelCase** (`"givenName"`) |
| `update_properties=[...]` in a modify request | **camelCase** (`"scheduleStatus"`) |
| Untyped condition constructors (`equal_to("givenName", ...)`) | **camelCase** |
| `data={"UserEntity": [...]}` type-name keys | the class name as a string |

When in doubt: the *typed* builder lets you keep writing snake_case; the *string*
APIs expect the wire camelCase name.
